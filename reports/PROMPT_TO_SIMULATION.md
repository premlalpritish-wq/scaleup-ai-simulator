# Prompt-to-insulin-simulation V0 — implementation report

**Definition.** A first-time user opens ScaleUp, describes the Zielinski
insulin process in words, presses **Generate simulation**, and receives the
existing evidence replay configured and executed through the existing Python
runner. The user selects no model, edits no JSON and does not touch Python.

**Workflow implemented:** Prompt → Interpret → Configure → Validate → Execute →
Visualise.

---

## 1. What was built

| Layer | Implementation |
|---|---|
| Prompt input | `scenes/prompt_simulation.tscn` + `scripts/prompt_simulation.gd`, opened from the workshop's **Prompt to simulation** button. |
| Interpreter | `composition/composition/prompt.py` — deterministic local rules over the Zielinski manifest. |
| Configuration | The original `composition/replay/zielinski_replay.json` loaded in memory with validated `literal_inputs`; the source file is never edited. |
| Validation | Port existence, input direction, quantity, unit conversion, finite value, required inputs, and duration against the published trajectory. |
| Execution | New `--interpret-prompt` and `--run-prompt` commands in `composition/composition/runner.py`, calling the existing `run_graph`. |
| Visualisation | Existing `ReplayVesselView`, `GrowthChart` and `CascadeChart` bound to the result through `ReplayData`. |
| Results | Requested-output table with value, unit, provenance/citation; warnings; assumptions; baseline comparison. |

No simulation engine, equation, model parameter or scientific value was added.

---

## 2. There is no LLM integration in this repository

A repository-wide search found no OpenAI/Anthropic/Gemini/Ollama client, API key,
endpoint or prompt service. V0 therefore does **not** add a cloud or paid
dependency. The interpreter is a local, auditable vocabulary of aliases and
regexes. Its output says `llm_used: false` and
`interpretation_method: "local_rules"`.

This means:

* it cannot invent an arbitrary equation or execute generated code;
* an unknown parameter, process or output becomes a clarification or rejection;
* it is reproducible offline.

If an LLM is added later, it should be constrained to produce this same
structured document and must still pass `prompt.validate_graph`; it must not
emit equations or bypass the manifest.

## 3. Structured interpretation

`python -m composition.runner --interpret-prompt "<text>"` returns:

```json
{
  "ok": true,
  "status": "ready_with_warnings",
  "target_process": {"supported": true, "...": "..."},
  "selected_model": {"model_id": "zielinski2019.rhi_process", "model_version": "1.0.0"},
  "duration": {"requested_hours": 19, "published_max_hours": 19},
  "requested_variables": ["OD600", "wet biomass", "inclusion bodies", "insulin activity"],
  "requested_outputs": ["real manifest port ids"],
  "requested_parameters": ["real input port ids and converted values"],
  "configuration": {"literal_inputs": {"zielinski_replay/<port>": {"value": 8.0}}},
  "validation": {"ok": true, "errors": []},
  "missing_information": [],
  "clarification": [],
  "assumptions": ["..."],
  "warnings": ["..."],
  "llm_used": false
}
```

The examples under `composition/examples/prompt_*_interpretation.json` are
generated by this command.

## 4. Example prompts

### A. Supported run

> Simulate the Zielinski insulin production process for 19 hours and show OD600,
> wet biomass, inclusion bodies and insulin activity.

Result:

* process supported; model `zielinski2019.rhi_process@1.0.0`;
* outputs map to the 19 real `stream:S02_culture_broth#od600_h*` ports, plus
  `node:N02#wet_biomass_g_per_L`, `node:N03#inclusion_bodies_g_per_L`,
  `node:N03#inclusion_body_fraction_of_biomass` and `node:N15#batch_activity`;
* no parameter changes; execution runs the original graph;
* 196 output ports compared with the unmodified replay: **0 differ**.

### B. Supported configuration change

> Increase the starting medium volume to 8 L and show wet biomass and insulin
> activity.

Result:

* `node:N01#starting_medium_volume = 8.0 L` in `literal_inputs`;
* validation passes (quantity `volume`, unit `L`);
* the configured run executes through the existing runner;
* three published derived values change, because the existing accounting
  identities use the volume: wet biomass 56 → **28 g/L**, inclusion bodies
  14.5 → **7.25 g/L**, and batch activity 10800 → **21600 IU**. The result names
  the differing ports and claims no causal mechanism beyond the run.
* other published values, including the AU cascade, remain unchanged; the
  original replay is still run beside the configuration for comparison.

### C. Clarification

> Simulate 48 hours of the insulin process.

Result: `needs_clarification`; code `duration_not_available`; options “Use at most
19 h” or “Supply a trajectory or kinetic model that extends this range”. Nothing
is executed.

### D. Unsupported process

> Simulate CHO cell insulin production for 48 hours.

Result: `rejected`; code `process_not_supported`; the CHO request is not mapped
onto the E. coli Zielinski model.

### E. Unavailable output

> Simulate the insulin process and show dissolved oxygen.

Result: the run is allowed, but `node:N01#dissolved_oxygen` is marked
`available: false` with the model's own reason. No value is invented.

## 5. Godot screen

From the workshop header, **Prompt to simulation** opens:

* **A. Prompt input** — multi-line editor, example selector, **Generate
  simulation** and **Interpret only**.
* **B. Interpretation** — process, selected model, duration, requested
  variables, parameter changes, missing information, assumptions, warnings,
  validation errors.
* **C. Simulation** — execution status and **Run validated configuration**.
* **D. Results** — the existing 3D vessel view, interactive `GrowthChart`
  (scrub updates the vessel OD encoding), `CascadeChart`, requested-output
  table with provenance/citation, baseline comparison, warnings and assumptions.

Generate simulation interprets and automatically executes when validation
passes. A clarification clears the old result and executes nothing, so a stale
run cannot look current.

## 7. Limitations

* **The Zielinski model is an evidence replay, not a predictive kinetic model.**
  Parameter changes can alter the validated configuration but cannot create a
  new scientific response unless the model has an equation for it. The result
  explicitly compares against the original replay and reports whether any
  published output changed.
* **Only one target exists in V0.** Any other organism, product or process is
  rejected rather than approximated.
* **Duration is bounded by the published trajectory.** The model publishes
  points to 19 h. A longer request is a clarification; no extrapolation is
  fabricated.
* **Parameter ranges are not declared by the model**, so validation covers port
  identity, type, quantity, unit, direction and required inputs. It does not
  invent numeric biological ranges.
* **The alias vocabulary is finite.** An unlisted phrase becomes missing
  information or a rejection. This is intentional; a matched word is never
  enough to select an arbitrary value.
* **No literature search is performed.** The feature is local and offline.
